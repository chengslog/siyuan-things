# 版本管理规则

SiYuan Things 使用语义化版本号 `MAJOR.MINOR.PATCH`，Git 标签在版本号前加 `v`，例如 `v0.3.1`。

`package.json`、`plugin.json`、Git 标签和 GitHub Release 的版本必须完全一致。

## 当前阶段：0.x

在发布 `1.0.0` 前，按以下规则确定版本：

| 变更类型 | 升级方式 | 示例 |
| --- | --- | --- |
| 仅修复 BUG、样式问题、性能问题或内部重构，没有新增用户能力 | 升 `PATCH` | `0.3.0 → 0.3.1` |
| 包含任何用户可见的新功能、新设置、新交互或兼容的数据能力 | 升 `MINOR`，并将 `PATCH` 归零 | `0.3.4 → 0.4.0` |
| 包含不兼容的数据、配置或交互变更 | 升 `MINOR`，并在更新日志中标明迁移或影响范围 | `0.4.2 → 0.5.0` |
| 仅修改文档、测试或发布脚本，不需要向用户发布 | 不升级版本 | — |

一个版本同时包含新功能和 BUG 修复时，按影响更大的类型升级：只要有新功能，就升级 `MINOR`，不能继续增加 `PATCH`。

以当前已发布的 `v0.2.18` 为基准：

- 下一次只有修复：发布 `v0.2.19`。
- 下一次包含新功能：发布 `v0.3.0`。
- `v0.3.0` 发布后的修复依次使用 `v0.3.1`、`v0.3.2`。

## 进入 1.0.0

满足以下条件后发布 `1.0.0`：

- 任务、项目、区域、标签和设置的数据结构已稳定，并具备必要的迁移方案。
- 核心工作流完成一轮发布前人工验证，没有已知的阻断性问题。
- README、隐私说明、更新日志和集市信息与实际功能一致。
- 已能对后续版本提供明确的兼容性承诺。

从 `1.0.0` 开始严格遵循 SemVer：

- `PATCH`：向后兼容的 BUG 修复。
- `MINOR`：向后兼容的新增功能。
- `MAJOR`：不兼容的数据、配置、接口或核心交互变更。

## 预发布版本

需要公开测试时使用 `-beta.N` 或 `-rc.N`，例如 `0.3.0-beta.1`、`0.3.0-rc.1`。

预发布版本只能在发布工作流能够将其标记为 GitHub Prerelease、且不会成为 Latest 或被思源集市抓取后使用。正式版发布时去掉预发布后缀，例如 `0.3.0-rc.2 → 0.3.0`。

## 更新日志规则

- 按自然日汇总，每个日期只保留一个一级版本记录，不因同一天多次补丁发布重复日期。
- 日期标题包含当天涉及的版本或版本范围，例如 `2026-08-27（v0.2.15–v0.2.18）`。
- 内容分为“新增功能”和“BUG 修复”，只保留有内容的分类。
- 同一项改动只记录一次，使用面向用户的结果描述，避免提交记录式的实现细节。
- 不兼容变更必须明确标注影响范围、迁移方法和是否可能导致数据变化。

## 发布检查清单

1. 根据本规则确定新版本号。
2. 同步修改 `package.json` 与 `plugin.json`。
3. 更新中英文 README、`CHANGELOG.md` 和相关发布文档。
4. 运行 `npm test` 与 `npm run build`，检查生成的 `package.zip`。
5. 提交代码，创建与插件版本一致的 `v<version>` 标签。
6. 推送 `main` 和标签，确认 GitHub Actions 成功。
7. 确认 GitHub Release 为正式 Latest，且包含 `package.zip`；思源集市随后异步抓取该版本。
